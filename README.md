# Amazon EKS Infrastructure & Observability Stack (`zoop-cluster`)


This repository contains Infrastructure as Code (IaC) utilizing **Terraform**  to provision a managed AWS Elastic Kubernetes Service (EKS) cluster, alongside native **Kubernetes manifests** and **Helm charts** to deploy and monitor a resilient web application within the kube-prometheus-stack observability ecosystem.

---

## 🏗️ Architecture Overview

The system architecture spans across AWS infrastructure and native Kubernetes layers:

* **Custom VPC Network:** Dedicated `10.0.0.0/16` isolation with public subnets spanning multiple Availability Zones (`us-east-1a` and `us-east-1b`), preconfigured for Kubernetes Elastic Load Balancers (`kubernetes.io/role/elb = 1`).
* **Administrative Bastion Host:** A secure `t2.micro` Ubuntu instance pre-bootstrapped via `user_data` to install the AWS CLI, `kubectl`, and automatically register the EKS `kubeconfig`.
* **EKS Cluster Core:** Managed control plane orchestrating a resilient `t2.medium` Node Group.
* **Metrics & Monitoring Engine:** Core Kubernetes metrics pulled via `metrics-server`, feeding into a full Prometheus operator deployment managed via Helm.
* **Application Workspace:** An isolated namespace (`devops-assignment`) running a resource-bounded, health-checked Nginx backend scaled across replicas.

Ensure your local system contains the following tools:

* [Terraform](https://developer.hashicorp.com/terraform/downloads) (v1.0+)
* [AWS CLI](https://aws.amazon.com/cli/) installed locally
* [Helm](https://helm.sh/docs/intro/install/) (v3+) installed on your management machine/bastion

## 🚀 Step-by-Step Deployment Guide

### Phase 1: Infrastructure Provisioning (Terraform)

#### 1. Configure Local Environment Variables

Navigate into the `EKS-Setup` directory and configure your temporary AWS access credentials in `aws.ps1`. Run the script to inject them into your active PowerShell terminal session:

```powershell
cd EKS-Setup
.\aws.ps1

```

> ⚠️ **CRITICAL SECURITY NOTE:** Never commit your actual AWS Access Keys to GitHub. Ensure `EKS-Setup/aws.ps1` is appended to your `.gitignore` file before pushing your code.

#### 2. Initialize and Apply Core Infrastructure

Run the following blocks to deploy your VPC network, Bastion host, and EKS Cluster (this stage takes roughly **10–15 minutes**):

```powershell
terraform init
terraform plan
terraform apply --auto-approve

```

### Phase 2: Interfacing with the Cluster via Bastion

Because infrastructure controls are locked down, management actions are performed using the Bastion Host.

#### 1. SSH into the Bastion Endpoint

Retrieve the public IP address generated by Terraform and connect using your secure keypair:

```powershell
terraform output bastion_public_ip
ssh -i "zoop-key.pem" ubuntu@<bastion_public_ip>

```

#### 2. Verify Your Context

The instance's automation layer automatically mounts your EKS keys onto your terminal profile. Run a quick validation test:

```bash
kubectl get nodes

```

### Phase 3: Setting Up Monitoring & Applications

From your cluster management context, install the metrics server and core observability engine components:

#### 1. Install Kubernetes Metrics Server

Deploy the standard cluster metrics engine required for baseline resource metrics (`kubectl top` command data tracking):

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

```

#### 2. Deploy `kube-prometheus-stack` via Helm

Add the Prometheus community charts repository and spin up your core tracking operators inside a dedicated `monitoring` namespace:

```bash
# Add and sync helm charts repository
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# Install the prometheus-stack chart components
helm install monitoring-stack prometheus-community/kube-prometheus-stack --namespace monitoring --create-namespace

```

Maps internal Prometheus and Grafana operator cluster endpoints onto visible AWS NodePort ranges to enable external web browser access:

## 📊 Dashboard PromQL Queries (Optimized)

### 1. Pod CPU Dashboard

Uses pre-aggregated recording rules to calculate efficient core usage without heavy on-the-fly math.

```promql
sum(node_namespace_pod_container:container_cpu_usage_seconds_total:sum_irate{namespace="devops-assignment"}) by (pod)

```

### 2. Pod Memory Dashboard

Tracks the exact working set memory, which is the primary metric the Kubernetes OOM (Out Of Memory) Killer uses to evaluate termination targets.

```promql
sum(container_memory_working_set_bytes{namespace="devops-assignment", container!=""}) by (pod)

```

* **Grafana Configuration Tip:** Set the panel unit configuration to **Data (Metric) -> Bytes** so raw numbers auto-render cleanly into MB or GB.

### 3. Pod Restart Dashboard

Tracks rapid container restarts over a tight, rolling time window.

```promql
sum(increase(kube_pod_container_status_restarts_total{namespace="devops-assignment"}[5m])) by (pod) > 0

```

* **The `> 0` filter:** Limits noise by ensuring the dashboard only populates pods actively experiencing instability.

### 4. Health Check Evaluation

Instantly targets pods that have shifted out of standard `Running` or `Succeeded` operational lifecycle phases.

```promql
sum(kube_pod_status_phase{namespace="devops-assignment", phase=~"Failed|Unknown|Pending"}) by (pod) > 0

```

## 🚨 Grafana Alert Setup Guide (`AppHealthCheckAlert`)

Follow these configuration steps to bind these metrics to a unified alert rule that fires if your backend flatlines or encounters a crash loop.

### Step 1: Create a New Alert Rule

1. Hover over the **Alerting** (bell) icon in the main sidebar and select **Alert rules**.
2. Click **Create alert rule** at the top right of the screen.

### Step 2: Name & Define Rule Type

* **Name:** `AppHealthCheckAlert`
* **Rule type:** `Grafana managed alert`

### Step 3: Configure the PromQL Expression

Select your Prometheus data source under **Query A** and paste the combined validation logic:

```promql
(sum(kube_deployment_status_replicas_available{deployment="backend", namespace="devops-assignment"}) by (namespace) == 0) + 1 
or 
(sum(increase(kube_pod_container_status_restarts_total{namespace="devops-assignment"}[5m])) by (namespace) > 2)

```

#### Query Execution Settings:

* **Type:** `Instant` (Forces a single execution snapshot rather than pulling down a heavy line graph)
* **Format:** `Table`

### Step 4: Map the Condition Evaluator

In the **Alert condition** (or Condition C) panel, establish the mathematical trap:

* **WHEN QUERY:** `A`
* **Evaluator:** `Is above`
* **Value:** `0`

> 💡 **Why this works:** If the deployment drops to 0 replicas, the query yields `1` (`0 == 0` evaluates to true, then adds `1`). If restarts cross your limit, the query also yields a positive integer. Since any failure state evaluates above `0`, the alert instantly trips!

### Step 5: Assign Folders & Labels

* **Folder:** Select or create a folder named `EKS-Observability`.
* **Evaluation group:** Create a new group named `app-health-group`.
* **Labels:** Click Add labels and assign `severity = critical`.

### Step 6: Define Evaluation Intervals & Buffers

Under **Set evaluation behavior**:

* **Evaluation interval:** `1m` (Evaluates the query rules every 60 seconds)
* **Pending period (For):** `2m` (Ensures minor deployment rollouts or network blips don't wake engineers up; the failure state must hold for 120 seconds before going red)

### Step 7: Description & Save

* **Summary:** `Application Down or Pod Crashlooping`
* **Description:** Tracks total backend service dropouts or aggressive pod restarts within the devops-assignment namespace.
* Click **Save rule and exit** at the top right.

## 🧪 Chaos Engineering Validation Tests

Use these commands on your cluster to simulate failures and verify your metrics and thresholds react correctly:

### Test Case A: Simulate Pod Failure (Process Death)

Force an immediate application error by killing the PID 1 process inside a live backend pod:

```bash
# Locate active pod name, then kill its parent process
kubectl exec <backend-pod-name> -n devops-assignment -- kill 1

# Verify the container restarted instantly and increased metric count
kubectl get pods -n devops-assignment

```

### Test Case B: Simulate Complete Outage (Deployment Dropout)

Scale the application deployment entirely down to zero replicas to watch the condition query hit the alerting threshold:

```bash
# Drop application availability to zero
kubectl scale deployment backend -n devops-assignment --replicas=0

# Verify availability status is down
kubectl get deployments -n devops-assignment

```

## 📝 6. Known Issues & Assumptions

* **Ephemeral Storage Assumption:** The `kube-prometheus-stack` is deployed using standard Helm chart defaults. This means Prometheus time-series data and custom Grafana dashboards are stored in the pods' ephemeral container layers. If a node fails or a pod is recreated, historical metric data and dashboard updates will reset unless a Persistent Volume Claim (PVC) backed by AWS EBS or EFS is provisioned.
* **Bastion Host Network Access:** To facilitate straightforward configuration during this evaluation window, the Bastion Host's security group allows inbound SSH (`Port 22`) from any IP address (`0.0.0.0/0`). In a production setting, this would be locked down tightly.
* **Public Worker Node Access (NodePorts):** The cluster exposes Prometheus (`30090`) and Grafana (`30000`) globally across the public IPs of the managed worker nodes. This assumes the evaluator needs direct browser access without configuring complex VPN tunnels or private corporate proxies.
* **Single-AZ Node Group Risks:** While the VPC spans across multiple Availability Zones (`us-east-1a` and `us-east-1b`) for subnet infrastructure compliance, the active worker nodes are running on a lightweight single Node Group pool. A localized AWS AZ outage would result in temporary service degradation.

## 🚀 7. What to Improve for Production

If migrating this setup from a local proof-of-concept assignment into a hardened, production-ready enterprise ecosystem, the following architectural enhancements would be prioritized:

1. **Ingress Controllers & Layer 7 Load Balancing:** Eliminate raw `NodePorts` completely. Deploy the **AWS Load Balancer Controller** to provision an Application Load Balancer (ALB). Route dashboard traffic through an Ingress resource mapped to dedicated corporate subdomains (e.g., `grafana.company.com`) fully protected with automated SSL/TLS certificates via AWS Certificate Manager (ACM).
2. **Stateful Persistence & High Availability:** Attach dedicated Amazon **EBS (Elastic Block Store)** or **EFS (Elastic File System)** `StorageClasses` to the Prometheus and Grafana stateful sets. This ensures metrics survive regular cluster node scaling, rolling updates, and unexpected pod rescheduling.
3. **Strict Network Isolation (Zero-Trust Private Topology):** Migrate all EKS managed worker nodes and internal databases out of the public subnets into isolated **Private Subnets**. Route outbound internet dependencies through a secure, high-availability **NAT Gateway**. Additionally, replace the Bastion Host with **AWS Systems Manager (SSM) Session Manager** to eliminate open ports entirely.
4. **Dedicated Notification Routing & Email Alerting:** Extend the Prometheus Alertmanager or Grafana Alerting Engine to route the `AppHealthCheckAlert` payload directly to an Amazon Simple Notification Service (SNS) topic or simple mail transfer protocol (SMTP) relay server to distribute critical real-time engineering emails the instant an operational boundary is reached.
